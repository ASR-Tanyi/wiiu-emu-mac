# Wii U Emulator for macOS — Implementation Plan

**Project:** `wiiu-emu` — a Wii U (Cafe) emulator written in modern C++ (C++20), targeting macOS on Apple silicon.
**Renderer:** **native Metal** via `metal-cpp`. Metal 3 baseline (macOS 13+), Apple7 GPU family (M1/A14+) required for the geometry-shader path.
**Status:** M2 reached (homebrew runs to `main()` and prints); Phase 7 done and run on the Mac — Metal pipelines, draws, heaps, the presenter, OSScreen and frame capture. Phase 8 under way: PM4, the register file, the GPU timeline (ADR-004), and GX2's command buffers, timestamps, vsync and swaps are in. GX2's scan buffers are in too, a GX2 flip reaches the window, and Latte's surface layout is in (ADR-005). GX2's surface calls are in as well, and so are `GX2ClearColor` and the scan-out copy, so a WHB title that only clears shows its colour in the window, and the depth buffer's twin calls are in beside them. The render targets, viewport and scissor are set as hardware sets them, GX2's context states work, with the GPU's state shadowing behind them, the depth, stencil, rasterizer, colour and blend calls are in, the GPU starts in GX2's default state, shaders can be bound, GX2 writes its own fetch shaders, attribute buffers and uniform blocks can be bound, and GX2's draw calls reach the command processor as draws. The shader decompiler (8.6) has begun: a program's control flow is decoded. Next: M3 on hardware, then the vertex fetch clause and the MSL for a first triangle.

## 0. Ground rules

### Legal / ethical scope
- This project emulates hardware. It ships **no** Nintendo code, **no** encryption keys, **no** system titles, **no** game data.
- The emulator reads content the user dumped from hardware they own. Key material (Wii U common key, per-console OTP, per-disc keys) is supplied by the user at runtime and never committed, embedded, or distributed.
- Anything that cannot be reimplemented cleanly gets a documented HLE stub, not a copied binary.

### Engineering rules
- **Every phase ends in something runnable.** No phase is "write 8000 lines and hope".
- **Tests before breadth.** A CPU instruction is not done until it passes a test; a format is not parsed until a real file round-trips.
- **Big-endian guest, little-endian host.** All guest memory access goes through typed byte-swapping accessors from day one. Retrofitting this later is a rewrite.
- **The host compiler does not decide how guest arithmetic rounds.** The build is `-ffp-contract=off` globally. Clang contracts `a * b + c` into a fused multiply-add wherever the target has one — always on arm64, never on x86-64 without `-mfma` — which is the same source producing two answers on two hosts. Espresso's `fmadd` really is fused and its `fmul`/`fadd` really are not, so the distinction is modelled with `std::fma` and the compiler is told to leave it alone. 10.4's replay and 12.7's lockstep both rest on this.
- **HLE-first.** Emulate Cafe OS libraries (`coreinit.rpl`, `gx2.rpl`, …) at the function level. LLE of the ARM security processor (Starbuck/IOSU) is explicitly out of scope except where a stub is insufficient.
- **Performance work is tracked separately** in [`docs/performance.md`](docs/performance.md) — 40 techniques (`P1`–`P40`) tagged by phase. Five of them are design constraints rather than later optimisations, and are flagged inline below.
- Prior art to read, not copy: **decaf-emu** (clean HLE architecture, R700 shader translator) and **Cemu** (mature, MPL-2.0, ships the only production Metal backend for this hardware). Both are worth studying; license boundaries respected.

### Platform decision: Apple silicon only
Metal is now the renderer, and the geometry-shader path depends on **mesh shaders**, which require GPU family **Apple7** — Apple silicon only. Intel Macs report Metal 3 but have no mesh shader support (Cemu explicitly vendor-blacklists Intel because its drivers claim Metal 3 and then break). Supporting Intel would mean writing a *second* geometry path as a compute pre-pass, on a platform where macOS 26 Tahoe is the last supported release and macOS 27 drops it entirely. **Target arm64 only.** Revisit only if a compute GS path turns out to be needed anyway for other reasons.

### Reference hardware
| Part | Detail |
|---|---|
| CPU | IBM **Espresso** — 3× PowerPC 750CL-derived cores, 1243.125 MHz (248.625 MHz bus; timebase 62.15625 MHz), 32-bit, **big-endian**, limited out-of-order (in-order retire) |
| L1 / L2 | 32 KB I + 32 KB D per core; L2 **asymmetric**: core0 512 KB, core1 2 MB, core2 512 KB |
| CPU ISA | 750CL + **paired singles** (`ps_*`, `psq_l/psq_st` with GQR quantization). **No AltiVec.** 32-byte cache lines, locked L1D + DMA (HID2, SPR 922/923) |
| Coherency | MERSI across the three L2s with intervention — cores *are* coherent. **Not** coherent with GPU/IO: software `DCFlushRange`/`DCInvalidateRange` required. `lwarx`/`stwcx.` are hardware-buggy; Cafe OS carries workarounds |
| GPU | AMD **Latte**, R700/TeraScale-derived, 549.999 MHz, 16 TMUs, 8 ROPs. (Shader-unit count is disputed: 160 vs 320. Irrelevant to emulation.) Command stream = **PM4 packets**; shaders = **R700 microcode** (CF + ALU/TEX clauses) |
| MEM1 | 32 MB on-die fast memory (1T-SRAM/eDRAM), phys `0x00000000`, virt `0xF4000000` |
| MEM0 | 3 MB SRAM, phys `0x08000000`–`0x082FFFFF` — kernel + IOS images |
| MEM2 | 2 GB DDR3-1600, phys `0x10000000`–`0xCFFFFFFF`. ~1 GB to apps, ~1 GB to OS |
| IOP | **Starbuck**, ARM926EJ-S inside Latte, ~96 KB SRAM, runs IOSU (crypto, FS, ES, USB, net) |
| Audio | DSP in Latte; **AX** API via `sndcore2.rpl`. 96 voices, 32 kHz **or** 48 kHz renderer, 3 ms frame (96/144 samples) |

## Phase 3 — Memory subsystem

**Goal:** a faithful guest address space that the CPU and GPU both see.

- [x] 3.1 Reserve a 4 GB `mmap` region as the guest address space; map MEM1/MEM2/MEM0 as sub-mappings so guest virtual → host pointer is a single add.
- [x] 3.2 Implement the Cafe OS virtual map from the table above; represent it as a table of `MemoryRegion { virtual, size, physical, flags, name }`.
- [x] 3.3 Typed accessors: `read<T>(addr)`, `write<T>(addr, value)` performing byte-swap; `translate(addr)` → host pointer. **⚠ Design for fastmem (P3) now.** Translation must reduce to `host_base + zero_extend32(guest_addr)` with no branch, with MMIO and unmapped access caught by a `SIGSEGV`/`SIGBUS` handler that decodes the faulting arm64 instruction. This removes a check from every guest load and store (10–40% of CPU time) and **cannot be retrofitted** onto an accessor API that assumed explicit checks.
- [x] 3.4 MMU model: BAT registers, segment registers, page table search. Start with a flat/identity fast path plus a fallback slow path that honours the real translation, so translation bugs surface but don't cost performance in the common case. *(`src/cpu/mmu.hpp`: eight IBAT/DBAT pairs with the upper four gated by HID4, sixteen segment registers, the hashed page table with both hashes, protection by PP and segment key, SR[N], reference and change bits, and a 256-entry direct-mapped TLB per side. Translation off is one test and the effective address passes through, so nothing is charged to the HLE path. Real addresses are mapped back through the region table, because Phase 3.1 keys the address space by virtual address — documented at the top of `mmu.hpp`, and the one place this deviates from hardware.)*
- [x] 3.5 MMIO dispatch: address ranges routed to device handler objects (GPU, audio, IPC, PI) rather than backing memory — left unmapped so the P3 fault handler routes them. Shares its handler with SMC detection (**P15**), so design the two together.
- [x] 3.6 Cache model: `DCFlushRange` / `DCInvalidateRange` / `DCZeroRange` / `ICInvalidateRange` must invalidate JIT blocks and mark GPU-visible ranges dirty. **Model the CPU↔GPU incoherency explicitly** — games depend on the flushes being real.
- [x] 3.7 Memory watchpoints for the debugger.
- [x] 3.8 Tests: region overlap assertions, read/write round-trips across region boundaries, MMIO routing.

**Done when:** a synthetic test writes through every mapped region and reads back correct big-endian values, and MMIO writes reach a fake device. ✅ *Phase 3 complete.*

## Phase 4 — PowerPC interpreter (Espresso)

**Goal:** a correct, slow, single-core interpreter. Correctness now; speed in Phase 12.

- [x] 4.1 `PPCCore` state, cacheline-aligned and laid out hot-fields-first to avoid false sharing between the three core threads (**P37**): 32 GPR, 32 FPR (each 2×f64 for paired singles), CR, XER, LR, CTR, MSR, SRR0/1, HID0-5, GQR0-7, SPRs, TB, DEC, SCR.
- [x] 4.2 Opcode decoder: generated from a declarative instruction table (primary opcode + extended opcode), producing both an interpreter dispatch table and a disassembler from one source of truth.
- [x] 4.3 Disassembler first — it makes every later bug tractable. Validated by **round-trip**: every instruction in the table is disassembled and fed back through binutils' PowerPC assembler, which must produce the identical word (`scripts/ppc_roundtrip.py`, wired into ctest). Stronger than diffing objdump text, since it checks meaning rather than spelling. 187/187 pass. Also ships `ppcdis`.
- [x] 4.4 Integer instructions: arithmetic, logical, compare, rotate/shift, load/store (incl. byte-reversed `lwbrx`/`stwbrx`, multiple `lmw`/`stmw`, string). Condition register ops.
- [x] 4.5 Branch unit: `b/bl/bc/bclr/bcctr`, link stack, `sc` system call trap.
- [x] 4.6 FPU: IEEE-754 double + single ops, `frsp` rounding, FPSCR flags, `fmadd` family with the correct non-fused/fused behaviour, `fres`/`frsqrte` estimate tables matching 750CL precision. *(Estimates are now the 32-entry base/decrement tables, and FPSCR is modelled properly: sticky exception bits with FX meaning "first one", VX and FEX recomputed as summaries rather than stored, FPRF, FI and FR, the enable bits, `mtfsf`/`mtfsb0`/`mtfsb1`/`mtfsfi`/`mcrfs`, and a program exception when an enabled exception fires with MSR[FE0]/[FE1] set. Overflow, underflow and inexact are read back from the host FPU running in the guest's rounding mode, so they come from the arithmetic rather than from a guess about it; FR for a double-precision result is recovered by re-evaluating toward zero. Two gaps remain, both dormant while Cafe OS leaves the enables clear: an enabled exception does not suppress the result write, and MSR[FP] is not consulted, so there is no floating-point-unavailable exception. **The estimate tables are now checked**: `frsqrte`'s matched Dolphin's hardware-derived table entry for entry, but `fres`'s first transcription had 26 of 32 bases wrong in the low bits and interpolated across thirteen mantissa bits instead of ten — all of it inside the architected 1/256, which is why the accuracy tests could not see it. It is now Dolphin's table and lookup (Gekko and Broadway share the 750CL's estimator), including saturation to ±FLT_MAX rather than ±infinity for inputs too small to invert, and bit-exact vectors in `test_fpscr.cpp` guard both.)*
- [x] 4.7 **Paired singles**: `ps_add/sub/mul/div/madd/msub/sel/merge/neg/abs/res/rsqrte/cmp`, and `psq_l/psq_lu/psq_st/psq_stu` with all GQR quantization types (float, u8, u16, s8, s16) and scale exponents.
- [x] 4.8 Supervisor: `mtmsr/mfmsr`, `mtspr/mfspr`, `rfi`, `tlbie`, cache instructions (`dcbz`, `dcbf`, `dcbst`, `icbi`, `dcbt`). *(Complete with 3.4: `mtsr`/`mfsr`/`mtsrin`/`mfsrin`, `tlbie`, `tlbsync`, the BAT and SDR1 SPRs, and a privilege check — supervisor instructions and SPRs now take a program exception in problem state, without which the MMU would be decorative. No `tlbia`: the 750 does not implement it. Cache instructions translate their effective address like any other access.)*
- [x] 4.9 Reservations: `lwarx`/`stwcx.` per-core reservation granule. Note the real hardware bug — model the *documented* behaviour, and add a compatibility switch if a title turns out to depend on the flaw.
- [x] 4.10 Exception model: decrementer, external interrupt, DSI/ISI, program, floating-point unavailable, system call. Vector table at `0x00000100`-relative offsets honouring `MSR[IP]`. **Note: the Cafe OS map has nothing at low addresses, so 6.2's loader must place a vector page before exception delivery works.**
- [x] 4.11 Timebase and decrementer driven from a host monotonic clock scaled to the timebase rate. *(Currently one tick per instruction — monotonic and proportional, not cycle-accurate, and deterministic, which 10.4 depends on. Hook to a host clock when frame pacing needs it. The rate is 62.15625 MHz: like every PowerPC 750 derivative the timebase counts the **bus** clock / 4, not the core clock / 4 — a factor of five that would have made every emulated second last a fifth as long.)*
- [~] 4.12 **Test suite**: port/adapt an existing PPC instruction test corpus; write a self-checking guest test harness; differential-test the FPU against a software reference. Target: every implemented instruction has at least one test, edge cases (overflow, NaN, denormal, carry) have their own. *(Integer/branch done: 520 golden vectors from an independent Python reference in `scripts/gen_cpu_fixtures.py`, plus six binutils-assembled programs. Extend with the FP work.)*

**Done when:** a hand-assembled PPC program computing a known result runs to completion, and the instruction test suite passes 100%.

**Note on `rfi` and the vector base**, found while testing 3.4 and worth remembering: `MSR[IP]` selects the vector base, so it must survive exception entry — clearing it with the rest of the mask sends every exception to the low addresses whatever the guest configured. And `rfi` restores only the architected MSR bits: SRR1 also carries the exception's cause, and copying it wholesale puts the core into power-saving mode on the way back from a privileged-instruction exception.

## Phase 6 — Kernel, scheduler, and coreinit HLE

**Goal:** a homebrew `.rpx` reaches `main()` and prints to the log. This is the first "it's alive" moment.

- [x] 6.1 HLE framework: a registry mapping `library.symbol` → native handler; automatic argument marshalling from PPC ABI (r3–r10 int, f1–f13 float, stack overflow) via templates, so a handler is written as an ordinary C++ function.
- [~] 6.2 Loader: resolve RPL dependency graph, map into the `0x02000000` region, allocate heaps per `cos.xml`, build the import trampolines, set up the initial stack and `r2`/`r13` SDA pointers.
- [~] 6.3 Three `PPCCore` instances on three host threads, plus a scheduler owning runnable-thread queues per core. Request `QOS_CLASS_USER_INTERACTIVE` so macOS keeps them off efficiency cores (**P34**). Add **idle-loop / spin detection (P2)** here, in the interpreter, before the JIT exists — guest threads spinning on `OSWaitEvent` or polled flags are pure waste, and skipping ahead is worth 1.5–3× on affected titles. Expose free-running vs lock-stepped cores as a setting (**P32**): free-running is not always faster. *(Threads still interleave deterministically on one host thread — that is what makes 10.4's record/replay and 12.7's JIT lockstep possible, and real parallelism goes behind the same interface when it is worth measuring. **P2 is done**, in both halves: the scheduler keeps every deadline (sleeping threads and alarms) in one list, so when nothing can run the clock jumps to the next one instead of the run loop emulating the wait; and the interpreter recognises a spin — a short backward branch taken repeatedly with no store, no counted branch, no pointer walk and no system call in between — so a thread polling a flag hands the core back in a few hundred instructions rather than at the end of its timeslice. `RunReport` reports both as `skipped_ticks` and `spin_yields`.)*
- [x] 6.4 `coreinit.rpl` — threads: `OSCreateThread`, `OSResumeThread`, `OSJoinThread`, `OSExitThread`, `OSYieldThread`, `OSSetThreadAffinity`, `OSSetThreadPriority`, thread-local storage.
- [x] 6.5 `coreinit.rpl` — synchronisation: `OSMutex`, `OSCond`, `OSEvent`, `OSSemaphore`, `OSRendezvous`, `OSFastMutex`, `OSMessageQueue`, spinlocks, atomic ops. *(All present. Two things worth remembering: a woken waiter resumes **after** its own lock call — the return address is set before the handler blocks it — so whoever unlocks has to name the new owner rather than leaving the mutex free, and a signalled condition variable has to hand its mutex to one waiter and queue the rest on it, or they resume unprotected. The atomics are plain reads and writes because guest threads interleave on one host thread and a handler runs to completion; they go through one helper, which is where the work lands if cores ever run in parallel (P32). Message queues are done too, and they are where the woken-waiter rule bites hardest: a receiver parked in `OSReceiveMessage` never looks at the queue again, so a send with someone waiting hands the message straight into the address that thread asked for rather than going through the ring, and a sender parked on a full queue leaves its message behind for whoever makes room. Queues are also the first object whose ordering the title can *see* in its own data, which is what turned up a scheduler bug worth naming: waiters were ordered by priority and then by `std::map` order, which is by handle — so which of two equal-priority threads was served first depended on where the title had allocated its `OSThread`s. Cafe OS thread queues are FIFO within a priority level; `Thread::block_sequence` now supplies the tiebreaker, for mutexes and events as much as for queues.)*
- [~] 6.6 `coreinit.rpl` — memory: `MEMCreateExpHeap`, `MEMCreateFrmHeap`, `MEMCreateUnitHeap`, `MEMAllocFromDefaultHeap`, the foreground/MEM1/MEM2 heap trio, `OSAllocFromSystem`. *(Expanded heaps, default/MEM1 heaps and the MEMAlloc family done. ## Phase 7 — Metal backend foundation

**Goal:** a Metal device, a swapchain, and the first Wii U pixels on screen.

### What Metal gives you, and what it doesn't

The renderer is native Metal, which is the right call — it's what Cemu ships, it's roughly 20–25% faster than the MoltenVK path, and it runs titles MoltenVK cannot. But Metal is a modern, deliberately narrow API and Latte is a 2008-era GPU. These gaps are **not** blockers, they are **shader-side emulation work** that must be designed in from the start:

| Latte needs | Metal status | Approach |
|---|---|---|
| Geometry shaders | **Absent** | Object + mesh shader pipeline (Apple7+). Also required for Latte **RECTS** primitives, not just real GS |
| Stream-out / transform feedback | **Absent** | `rasterizationEnabled = false` with a `void`-returning vertex function writing to `device` buffers; index output manually from `[[vertex_id]]`/`[[instance_id]]` — there is no hardware output counter. Use compute when a counter is genuinely needed |
| Provoking vertex control | **Absent** (private API only) | Bake flat-shading attribute selection into the shader, or rewrite index buffers |
| Non-seamless cube maps | **Absent** (private API only) | Metal cube sampling is always seamless; emulate in-shader if a title depends on the seam |
| Logic ops | **Absent** (private API only) | Shader logic ops via programmable blending / framebuffer fetch (Apple silicon only — the route Dolphin took) |
| Disabling primitive restart | **Impossible** — `0xFFFF`/`0xFFFFFFFF` are always restart indices | Rewrite the index buffer when Latte uses those as real indices |
| Custom sampler border colour | **Absent** — only `opaqueBlack`/`opaqueWhite`/`transparentBlack` | Emulate arbitrary border colour in-shader |
| Wide lines | **Absent** (line width fixed at 1.0) | Expand to quads if needed |
| Point fill mode | **Absent** (`.lines` and `.fill` only) | Draw points explicitly |
| Depth range `[-1,1]` | Metal is always `[0,1]` | Fold into the projection matrix |
| Vertex attribute alignment | Metal requires 4-byte alignment; Latte does not | **Manual vertex fetch inside the shader.** (Cemu tried a compute realign pre-pass and it was slower.) |

- [~] 8.1 `gx2.rpl` HLE surface: `GX2Init`, `GX2SetupContextStateEx`, `GX2SetContextState`, `GX2DrawEx`, `GX2DrawIndexedEx`, `GX2SwapBuffers`, `GX2WaitForVsync`, `GX2SetColorBuffer`, `GX2SetDepthBuffer`, `GX2SetViewport`, `GX2SetScissor`, `GX2Set{Vertex,Pixel,Geometry}Shader`, `GX2SetVertexUniformBlock`, `GX2InitTextureRegs`, `GX2CopySurface`, `GX2ClearColor`, `GX2ClearDepthStencilEx`. *(The skeleton is in — `hle::gx2`, registered under `gx2`: `GX2Init` (its attribute list read and the command-buffer pool noted, not used), `GX2Shutdown`, `GX2GetMainCoreId`, `GX2Flush`, the timestamp calls (`GX2GetLastSubmittedTimeStamp`, `GX2GetRetiredTimeStamp`, `GX2WaitTimeStamp`, `GX2DrawDone`), display lists (`Begin`/`End`/`Call`/`DirectCall`/`Copy`, write status, current list) and `GX2Set`/`GetEventCallback`. The copy detiles the viewed level (8.5's CPU detiler) into the scan buffer's frame, scaling by nearest pixel if the sizes differ; unorm and sRGB 8_8_8_8 copy as the same bytes, other mismatches are refused. **Which frame** is decided on the GPU's side: the swap packet is counted as it runs, and a copy lands in frame *swaps reached* of the rotation — the same count a flip shows its frame by — so a copy inside a display list called every frame fills each frame in turn; a test does exactly that. Problems with a packet are logged once, not every frame. **The depth buffer's twins** are in too: `GX2InitDepthBufferRegs` packs DB_DEPTH_SIZE/VIEW/INFO, the hierarchical-Z, prefetch and preload registers and the polygon-offset format control (`latte/depth_buffer.hpp`) — decaf's reading, since Cemu fills in only the size, on which they agree; the size, view and info fields and the depth formats are checked against Linux's `r600d.h`. `GX2ClearDepthStencilEx` writes the clear registers only where its flags ask (Cemu's four flags; decaf writes both every time and names two), then sends `HLE_CLEAR_DEPTH_STENCIL`, which clears depth, stencil or both when it runs, a packed stencil left alone by a clear of depth and the other way round. Elements are little-endian words — how Cemu, which runs real titles, reads depth back as a texture — so R16 is a 16-bit unorm, R24_X8 24 bits of depth under the stencil byte, and R32 the float itself; the float D24_S8 and the 64-bit X8_X24 are refused for now. **Binding them** is in as well (`gx2_state.hpp`): `GX2SetColorBuffer` writes a target's seven CB_COLORn registers and `GX2SetDepthBuffer` the depth buffer's, each with `SET_CONTEXT_REG` into the GPU's register file, as hardware does — the base being the level's physical address with the swizzle's bank and pipe bits in, shifted by 8, and the multisampled CMASK/FMASK registers from the AA buffer. `GX2SetViewport` and `GX2SetScissor`, and their `Init…Reg`/`Set…Reg` halves, write PA_CL_VPORT_* (with decaf's guard band and depth range) and PA_SC_GENERIC_SCISSOR_* (Cemu's: clamped to 8192, window offset off). Every register address is checked against Linux's R600 register list (`reg_srcs/r600`). **Context states** are in (`gx2_context.hpp`): `GX2SetupContextStateEx` clears the title's `GX2ContextState`, names its six register images as the GPU's shadow blocks so the state written after it lands there, and records the binding — `CONTEXT_CONTROL` and six `LOAD_*` packets — in the block's own display list; `GX2SetContextState` calls that list (or writes the packets, for a state set up without one), and with NULL turns shadowing off; `GX2GetContextStateDisplayList` hands the list out. **The depth, stencil and rasterizer calls** are in too (`gx2_state.hpp`, fields in `latte/render_state.hpp`): `GX2SetDepthStencilControl` and `GX2SetDepthOnlyControl`, `GX2SetStencilMask`, `GX2SetPolygonControl` and `GX2SetCullOnlyControl`, `GX2SetPolygonOffset`, `GX2SetPointSize`, `GX2SetPointLimits`, `GX2SetLineWidth`, `GX2SetRasterizerClipControl` (and `Ex`, `HalfZ`) and `GX2SetPrimitiveRestartIndex`, with the `Init…Reg`/`Set…Reg` pairs where GX2 has them. DB_DEPTH_CONTROL's fields are checked against Linux's `r600d.h`, PA_CL_CLIP_CNTL's against AMD's R6xx register reference, the rest are decaf's and Cemu's tables, which agree; two values differ between them and Cemu's are taken — sizes clamped to 16 bits rather than wrapped, and DX_LINEAR_ATTR_CLIP_ENA set by the clip control. `GX2SetDepthStencilControl` takes thirteen arguments, so the HLE marshaller now reads arguments past r10 and f8 from the caller's parameter area at 8(r1) — a word for an int or a float, eight aligned bytes for a 64-bit value or a double, as `powerpc-linux-gnu-gcc` lays them out; before, they read as zero. **The colour calls** follow the same pattern: `GX2SetColorControl`, `GX2SetBlendControl` (eight targets; a ninth is refused), `GX2SetBlendConstantColor`, `GX2SetTargetChannelMasks`, `GX2SetAlphaTest`, `GX2SetAlphaToMask` and `GX2SetAAMask`, each with its `Init…Reg`/`Set…Reg` pair. CB_TARGET_MASK's nibbles and CB_COLOR_CONTROL's SPECIAL_OP are checked against Linux's `r600d.h`, the blend, colour-control and alpha-test fields are decaf's and Cemu's, which agree, and alpha-to-mask's dither offsets and the AA mask are decaf's alone. The layout and the register ranges are decaf's and Cemu's, which agree entry for entry; on the values they differ on — the `CONTEXT_CONTROL` bits, the config load's second word — Cemu's are taken, and decaf's naming a new block without loading it. **The default state** is in as well: `GX2Init` now starts the GPU the way GX2 does — shadowing off, GX2's register initialisation, `GX2SetDefaultState`, all submitted, so a title's first timestamp is 2 — and every new context state is given the same, so binding one gives back a complete state. Both sequences are decaf's, which read them out of gx2.rpl; Cemu writes far less. Linux's R600/R700 headers name all but three of the registers decaf leaves unnamed (PA_SC_FORCE_EOV_MAX_CNTS, VC_ENHANCE, SPI_THREAD_GROUPING, SX_SURFACE_SYNC, DB_DEBUG, PA_SC_EDGERULE…), and one of decaf's writes is moved to where its own names say: it writes PA_SC_MPASS_PS_CNTL and PA_SC_MODE_CNTL at PA_SC_LINE_STIPPLE's address, which would put the mode control in VGT_OUTPUT_PATH_CNTL. A neat cross-check came out of it: the first range a binding's config load restores is exactly the six registers `GX2SetShaderModeEx` writes. That call is in (`gx2_shader.hpp`), all four modes, decaf and Cemu agreeing but for Cemu's four clause temporaries in every mode, which are taken; so are `GX2SetStreamOutEnable` and the tessellation levels, while `GX2SetTessellation` is a stub, as it is in decaf. The command processor takes `SET_ALL_CONTEXTS` as a context-register write. **Binding shaders** is in (`gx2_shader.hpp`): `GX2SetFetchShader`, `GX2SetVertexShader`, `GX2SetPixelShader` and `GX2SetGeometryShader` read the title's shader structures — decaf's layouts, offsets pinned — and write their registers in decaf's order: the program's start, size and resources (the program found through the structure's pointer or, when that is null, its GX2R buffer), then the stage's own — the vertex shader's outputs and semantics, or in geometry mode its ES registers; the pixel shader's inputs, exports and shader controls; the geometry shader's copy shader as the VS stage. Cemu writes a subset of each; where the two differ it is named in the code — the two unnamed words after a program's size (0x100000 throughout), DB_SHADER_CONTROL's dual export, which decaf has GX2 turn on, and SQ_PGM_EXPORTS_PS, which Cemu leaves out. The command processor now carries out SQ_VTX_SEMANTIC_CLEAR, emptying the semantics it names (decaf's reading). `GX2Get…ShaderGPRs`/`StackEntries`, the uniform registers (`GX2SetVertexUniformReg`/`PixelUniformReg`, into the ALU constants) and `GX2Invalidate` (a SURFACE_SYNC with decaf's cache bits, which Linux's `r600d.h` names; still recognised and not acted on until there are caches, 8.13) come with it. Every address is in Linux's R600/R700 headers. **The fetch shader** is in (`gx2_fetch_shader.hpp`): `GX2InitFetchShaderEx` generates it from the title's attribute streams — one semantic vertex fetch per attribute, sixteen to a VTX_TC clause, then a RETURN — and writes it into the title's buffer little-endian, as the GPU reads it, with `GX2CalcFetchShaderSizeEx` and `GX2GetAttribFormatBits` beside it. The microcode words are named in `latte/microcode.hpp`, where the decompiler (8.6) will read them. decaf and Cemu generate the same program but for four things, each named in the code: GX2's 10_10_10_2 attribute is FMT_2_10_10_10 (0x19) in Cemu's table and FMT_10_10_10_2 in decaf's switch — Cemu's is taken, the number GX2's own surface formats give R10_G10_B10_A2; decaf's mega-fetch fields are taken; the structure is cleared first, as Cemu does (decaf reads its divisor count before setting it); and the program's register count is decaf's zero, not Cemu's two. Instance divisors become the step rates the way Cemu searches them, which keeps a third divisor from writing past the array as decaf's does. Only the untessellated fetch shader is generated — decaf refuses the others, Cemu writes the untessellated one regardless, as this does, logged — though `GX2CalcFetchShaderSizeEx` gives decaf's tessellated sizes. **Attribute buffers and uniform blocks** are in (`gx2_buffers.hpp`, the resource window's layout in `latte/resources.hpp`): `GX2SetAttribBuffer` writes a buffer resource for one of sixteen attribute buffers, which the fetch shader's buffer 0xA0 + n reaches — resource 0x140 + n, past the vertex stage's 160 — and `GX2SetVertexUniformBlock`, `GX2SetPixelUniformBlock` and `GX2SetGeometryUniformBlock` write one at the stage's 0x80th resource on, and the stage's constant-cache base and size besides, which is what a shader's ALU reads a uniform block through. The GX2R forms do the same from an offset into a GX2R buffer. decaf's sequences; Cemu agrees on every word but three things, named in the header: it shifts an attribute buffer's stride by 11 where Linux's `r600d.h` has 8 (Linux's is taken), writes a uniform block's word 2 as zero where decaf gives its stride and format, and puts its pixel uniform blocks at a window offset that is not a resource boundary — and its VS and GS offsets, 0x7E0 and 0xCB0 words in, are exactly decaf's resources, which a test checks. Where decaf's GX2R attribute call passes the whole buffer's size, Cemu's passes what is left past the offset, as both do for uniform blocks; Cemu's is taken. `latte::buffer_resource` reads one back for the translator. **The draw calls** are in too (`gx2_draw.hpp`, the draw registers' fields in `latte/draw.hpp`): `GX2DrawEx` and `GX2DrawIndexedEx`, their `Ex2` forms, which set a base instance around the draw and put it back to zero, and `GX2RDrawIndexed`. Each writes the base vertex (SQ_VTX_BASE_VTX_LOC, a control constant), the primitive type, the index format for an indexed draw, the instance count and the draw packet — DRAW_INDEX_AUTO, or DRAW_INDEX_2 with the indices' physical address — and the command processor hands it to its draw listener with the register file as it stands, which is where the translator will take over; until then nothing draws. GX2's four index types are VGT_DMA_INDEX_TYPE's own values, which decaf works out and Cemu writes as they are; a test holds the two to each other. decaf's sequences again, Cemu's agreeing but for three things, named in the header: Cemu writes an index format before an auto-indexed draw as well, which decaf leaves out and such a draw does not read; Cemu sets the predicate bit on every draw packet, which decaf's writer cannot (its stream-out draw carries a to-do saying gx2.rpl does), and Cemu's is taken so that predication, when it arrives, is not ignored; and decaf marks a tessellated indexed draw with the initiator's major mode 1, which is taken. An unknown index type, or indices the GPU cannot see, is refused and logged. Not yet: GX2R's own buffers (`GX2RCreateBuffer`, the allocator, locking), which the GX2R forms will want before a title can use them; the `Get…Reg` calls; shaders' loop variables (decaf adds their offsets to the loop constants as bytes, Cemu writes none — to be settled by a title that has one); the tiling aperture `GX2Invalidate` would translate; SPI_THREAD_GROUPING in the shader mode for newer SDKs (Cemu writes it by the title's SDK version; GX2's initialisation writes it anyway); `GX2SetAAMode`; the shader invalidation a binding ends with; thick-tiled clears, those two depth formats, hierarchical Z, a multisampled copy's resolve (it shows sample 0), multisampled colour buffers' CMASK/FMASK (logged), swap interval 0 flipping without waiting (it waits like 1), the display-list overrun callback (a full list drops the rest, logged), `GX2SubmitUserTimeStamp`; the immediate draw (`GX2DrawIndexedImmediateEx`), whose indices travel in the packet and which decaf and Cemu pack differently for little-endian 16-bit indices — to be settled with the translator that unpacks them; stream-out draws and compute dispatch; and textures and samplers.)*
- [~] 8.2 **Command buffer model.** GX2 calls append PM4 to a ring buffer; the emulator runs a separate GPU thread consuming it, mirroring hardware asynchrony. Do not shortcut this into synchronous calls — timing-sensitive titles depend on the split. **The CPU blocks only where the guest actually asked it to (P4)**; every other wait is a bug, worth up to 2× on sync-heavy titles. Ship a "CPU stalls waiting on GPU per frame" counter alongside it — it should read near zero. *(→ **[ADR-004](docs/decisions/ADR-004-gpu-timeline.md): the GPU runs on the guest's clock.** A host thread reading the ring would make every guest-visible answer — a polled timestamp, a waited-on one, memory the GPU writes — a race against host timing, and break record/replay and the JIT lockstep the way free-running CPU threads would. So `latte::GpuTimeline` copies each submission when it is made, gives it a timestamp and a deadline one fixed latency (1 ms of timebase by default, a setting) after the tick it was submitted at, and **retires** it when the guest's clock reaches that deadline: its packets run, `MEM_WRITE` and `EVENT_WRITE_EOP` land in guest memory, end-of-pipe interrupts reach a listener, and the retired timestamp moves. Submissions retire in order whatever their ticks; the "GPU clock" a packet writes is the retirement tick, so the same stream writes the same bytes on every run, which a test checks directly. The timeline is on the scheduler's timer list — one timer, `gx2::gpu_timer_id`, re-armed at each next deadline — and waiting guest threads sleep until `deadline_of` (8.1). Still to do: when the translator has Metal work worth overlapping (8.11), the host encoding thread ADR-004 keeps behind the timeline. The CPU-stall counter is `FrameStats::cpu_stall_us`, already in place from 7.2.)*
- [~] 8.3 **PM4 parser**: Type-0 (base register + count), Type-2 (filler), Type-3 (opcode + size + predicate). Decode `IT_*` opcodes: `SET_CONFIG_REG`, `SET_CONTEXT_REG`, `SET_ALU_CONST`, `SET_RESOURCE`, `SET_SAMPLER`, `DRAW_INDEX_2`, `DRAW_INDEX_AUTO`, `INDEX_TYPE`, `NUM_INSTANCES`, `EVENT_WRITE`, `EVENT_WRITE_EOP`, `SURFACE_SYNC`, `CONTEXT_CONTROL`, `MEM_WRITE`. *(Reader and command processor done, in a new `wiiu::latte` library — Latte's formats stay out of `wiiu::gpu`, which is the backend interface (7.1). The reader splits a stream into packets exactly and **stops** at the first word it cannot frame — a payload past the end, or a Type 1 header, which R600-class parts do not have — because once one header is misread every packet after it is. The command processor writes Type 0 and every `SET_*` window into the register file, hands `DRAW_INDEX_AUTO`/`DRAW_INDEX_2`/`DRAW_INDEX_IMMD` to a listener with the register file as it stood *at that packet*, and runs `INDIRECT_BUFFER`(`_PRIV`) from guest memory, nested up to eight deep so a cycle in guest memory stops rather than exhausting the host stack. The packets that need the GPU thread to mean anything — `EVENT_WRITE(_EOP)`, `MEM_WRITE`, `WAIT_REG_MEM`, `SURFACE_SYNC` and the rest — are recognised and **counted by opcode** rather than guessed at; 8.2 acts on them. **State shadowing** is acted on: `CONTEXT_CONTROL` sets which windows load and which are shadowed, a `LOAD_*` (the eight of them) loads its ranges from guest memory and makes that block its window's shadow base, and while shadowing is on every `SET_*` into the window is written to the block as well, at the register's own offset — decaf's model, big-endian as Cemu keeps it. That is what GX2's context states are made of (8.1). `SET_ALL_CONTEXTS`, which GX2 uses for a register it wants in every context, is a context write here, where there is one context. Packets carry **physical** addresses, so `memory::to_virtual` now maps them back. The emulator's own packets — `0xF0` up, for work GX2 does on hardware with a draw or a DMA — go whole to a listener, GX2's (8.1).)*
- [~] 8.4 Latte register file: the full context/config register state, decoded into a structured `LatteContext` that pipeline creation reads from. *(The register file is done: one flat array over the 256 KiB register space, which is what Type 0 addresses, with each `SET_*` opcode confined to its own window — config, context, ALU constants, resources, samplers, and the control, loop and bool constants, at the R600 bases decaf agrees with. - [~] 8.5 **Surface/texture decoder**: Latte tiling modes (linear, 1D-tiled thin/thick, 2D-tiled, micro/macro tiling with bank/pipe swizzle), formats (R8G8B8A8, R5G6B5, BC1–BC5, depth D24S8/D32F, HW-specific ones), mip chains, array slices, 3D textures, cube maps. Element by element it is `element_offset`, which is addrlib's arithmetic per pixel — about 210 ms for a 720p frame in a debug build — so where a micro-tile is known to sit in one piece (linear and 1D, and the 2D/3D thin modes when a tile and its samples fit the 256-byte pipe interleave) it asks once per 8×8 tile and places the rest by the first tile's pattern: 26 ms in the same build. Still to do: the compute kernel (P26), depth formats, and the format conversions.)*
- [~] 8.6 **Shader decompiler.** Parse R700 microcode: CF clauses (ALU, TEX, VTX, EXP, loops, jumps, calls), ALU clauses (5-slot VLIW xyzwt, literals, previous-vector/previous-scalar), TEX/VTX clauses. Lower to an internal IR, then **emit MSL text directly**. *(**The control flow is decoded** (`latte/control_flow.hpp`, the words of all three instruction forms in `microcode.hpp`): `decode_control_flow` walks a program from its entry — to END_OF_PROGRAM, or for a fetch shader to its RETURN — follows CALLs into their subroutines, and lists every clause it runs, what kind and where. It refuses a program that runs off its end, an instruction R700 does not have (the common form past VTX_TC_ACK, an export not among the ten, the ALU clause's reserved 0xC, which is Evergreen's ALU_EXT), a clause or a jump outside the program, and a subroutine that never returns — so the later stages need not check again. `disassemble` prints it in AMD's syntax as decaf spells it. Next: the fetch clauses (VTX, then TEX), then the IR and the MSL for that triangle, then ALU clauses.)*
  - **Do not route through SPIR-V.** Apple's Metal Shader Converter takes DXIL, not SPIR-V, so the only SPIR-V→MSL path is SPIRV-Cross — and SPIRV-Cross's MSL backend has **no mesh shader support**, which kills the geometry-shader path outright. - [ ] 12.3 **macOS JIT mechanics**, all of which are required: `mmap(..., MAP_JIT, ...)`; the `com.apple.security.cs.allow-jit` entitlement (the mapping fails outright without it); Hardened Runtime + code signing; `pthread_jit_write_protect_np(0)` to write / `(1)` to execute, which is **per-thread**, not per-page — so a background compile thread can hold write permission while execution threads hold execute. **And: call `sys_icache_invalidate()` after emitting code** — arm64 has no coherent I-cache, and skipping this is the classic silent-corruption bug. (Phase 1.8 already proved the signing path.)
- [ ] 12.4 Block cache with invalidation driven by `icbi`/`ICInvalidateRange` and by writes to code pages.
- [ ] 12.5 Paired-singles and FPU codegen — the hard part, especially `frsqrte`/`fres` estimate tables and non-fused multiply-add semantics. NEON maps to paired singles reasonably well.
- [ ] 12.6 Optimisations in order of payoff (`docs/performance.md` Tier 2): **dead flag elimination first (P6)** — PPC CR/XER updates are mostly unused and this is the largest single PowerPC JIT win — then block linking (**P7**), inline caches plus a return-address stack (**P10**), and constant folding.
- [ ] 12.7 **Differential testing**: run interpreter and JIT in lockstep over the instruction test corpus and over real titles, diffing state every block. A JIT without this will produce bugs no one can find.
- [ ] 12.8 Tiered execution: interpret cold blocks, compile hot ones, with a profiling counter.

**Done when:** JIT output matches the interpreter bit-for-bit on the test corpus, and a title runs ≥5× faster.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Metal has no geometry shaders or stream-out | High | Mesh-shader GS path (8.8) and `rasterizationEnabled=false` stream-out (8.9), designed in from Phase 7 rather than bolted on |
| Mesh shaders require Apple7 — no Intel Mac support | Medium | Accepted: arm64-only (ADR-002). Intel is EOL in macOS 27 anyway. A compute-based GS path stays possible if ever needed |
| Metal gaps needing shader-side emulation (provoking vertex, logic ops, primitive restart, border colour, cube seams) | Medium | Catalogued in the Phase 7 table; the shader analysis pass (8.7) flags which shaders need which |
| Latte tiling/swizzle is under-documented | High | Build a tiling test harness early; cross-check against known-good decoders *(ADR-005: AMD's addrlib, cross-checked against Cemu's implementation — identical over 92M addresses)* |
| Shader decompiler complexity | High | Incremental: get simple shaders right, add CF/loop/branch support driven by real failures |
| HLE surface is enormous | Medium | Loud logging on unimplemented imports; implement strictly on demand |
| Espresso `lwarx`/`stwcx.` hardware bug | Medium | Implement documented behaviour; add a compat switch if a title depends on the flaw |
| Metal 4 deprecating the legacy tessellation path | Low | Target Metal 3 as baseline, treat Metal 4 as additive; verify before relying on tessellation |
| `MTLBinaryArchive` silently missing across OS versions | Low | Always pair it with our own on-disk cache (8.10) |
| Scope: this is a multi-year project | Certain | Phases 1–6 are genuinely achievable solo; ship at every milestone |

## Immediate next actions

1. **M3: an OSScreen homebrew in the window.** Build one with devkitPro + `wut` on the Mac — the `helloworld` sample, or anything using `WHBLogConsole` — and run `wiiu-emu --run hello.rpx --window`. 2. **Phase 8 continues: the state for a first draw.** Pixels reach the scan buffer — `GX2ClearColor` and `GX2CopyColorBufferToScanBuffer` — and WHB's depth buffer is set up and cleared beside them, so a `WHBGfx` sample runs its frame loop with nothing it calls before drawing missing. A WHB homebrew that clears should show its clear colour; nothing drawn will appear yet. The render targets (`GX2SetColorBuffer`, `GX2SetDepthBuffer`), viewport and scissor now reach the register file, and the context state WHB builds once and binds every frame works, the GPU's state shadowing behind it. The depth, stencil, rasterizer, colour and blend calls are in, and the default state, which `GX2Init` writes and every new context state holds. Shaders can be bound, with the uniform registers and `GX2Invalidate`, and `GX2InitFetchShaderEx` writes the fetch shader. Attribute buffers and uniform blocks can be bound (`GX2SetAttribBuffer`, `GX2Set…UniformBlock`, and their GX2R forms). The draw calls (`GX2DrawEx`, `GX2DrawIndexedEx` and their `Ex2` forms) reach the command processor's draw listener, which is where the translator (8.6, 8.11) takes over: the shader decompiler has begun with the control flow (8.6). decaf's example triangle shaders have no ALU at all — a CALL_FS and two exports in the vertex shader, one export in the pixel shader — so the shortest road to a first triangle is the vertex fetch clause, then an IR and MSL for exactly that, and only then ALU clauses. Textures and samplers, and GX2R's own buffers, are the GX2 calls still missing before a textured sample. 8.2's last piece, guest RAM wrapped for the GPU with `import_host_memory`, comes with the first draw that needs a buffer.
3. Decide what to do about MSR[FP]: nothing consults it, so there is no floating-point-unavailable exception, and a guest doing lazy FPU context switching would silently read stale registers.
